# Threats to Validity — AIDev Security Study

> Companion to `analysis/REPORT.md` (run_id `2026-04-26T18:57:09Z`).
> Section anchors `(§N)` reference REPORT.md unless noted otherwise.
> File-path anchors reference the repository root.

This document enumerates threats to validity for the canonical run of
the study. It is hand-authored — not regenerated from the Jinja
template — and should be re-read whenever `configs/*.{yaml,txt}` is
revised, when the AIDev dataset version changes, or when the matching
or FE-design defaults change.

The taxonomy follows Cook & Campbell (construct, internal, external,
statistical-conclusion). A final section lists threats that don't fit
that taxonomy cleanly but are worth surfacing.

---

## 1. Construct validity

Does the operationalisation correspond to the construct?

### 1.1 "AI-coded" is whatever AIDev v3 marked

`analysis/scripts/phase_a_cohort.py` filters AIDev's curated
`pull_request` table to the study window and treats membership as
ground truth for the AI cohort. The study inherits AIDev's
classification errors unmodified; AIDev's classifier
sensitivity/specificity is not republished in the report.

### 1.2 Asymmetric cohort definition

- AI cohort = "labelled agentic by AIDev v3."
- Control cohort = "not labelled by AIDev **and** does not match
  `configs/agent_fingerprints.yaml`" (11 short regexes such as
  `\bgenerated by\b`, `\bclaude code\b`, `\bcodex\b`,
  `\bgithub copilot\b.*\bagent\b`).

A repo using vanilla Copilot autocomplete with no PR-body footer lands
in the control pool. The two arms therefore have different error
structures, both biased toward attenuation.

### 1.3 Workflow-file presence ≠ effective security configuration

Phase C (`analysis/scripts/phase_c_tooling.py`,
`configs/tools.yaml` — 19 tools across 5 categories) matches `uses:`
coordinates and step-name keywords inside `.github/workflows/`. It
cannot tell that:

- a CodeQL job is commented out,
- a job is scheduled on a non-default branch only,
- the required-status check has been removed in branch protection,
- a step is wired with `continue-on-error: true`,
- the workflow file exists but is not invoked by any trigger.

The construct is "the action exists in YAML," not "scanning is
enforced." This is consistent with the large unadjusted-vs-adjusted
gap in §5.5 (see §2.1 below).

### 1.4 The "security intervention" construct is fragile

§9 documents that revising `configs/security_patterns.yaml` (now only
**13 keywords + 7 token regexes**) **flipped the sign** of RQ3's
`any_security_intervention` outcome:

| metric | pre-clean | post-clean |
| :-- | --: | --: |
| `agentic_intervention_rate` | 0.2147 | 0.0248 |
| `human_intervention_rate`   | 0.3453 | 0.0481 |
| `bot_keyword_hits_total`    | 14089 | 668 |

Robustness variant `v5_bot_identity_only` (§8.2) strips the keyword
detector entirely and confirms `any_security_intervention` is no
longer significant (OR=0.7234, p=0.296) without keywords. The
canonical RQ3 finding for that outcome effectively lives inside the
13 phrases the operator hand-picked.

### 1.5 `security_bots.txt` is a 14-bot allowlist

`configs/security_bots.txt` lists 14 bot logins (three added
2026-04-26 post-audit: `sonarqubecloud`, `socket-security`,
`deepsource-io`). Any vendor not in the file (Mend, GitGuardian,
Aikido, Endor Labs, JFrog Xray, Semgrep Cloud, Wiz, …) silently
scores zero. The same closed-vocabulary problem affects
`configs/tools.yaml` for RQ1/RQ2: tools outside the rule-set are
absent on both arms. If AI repos disproportionately adopt long-tail
tooling, RQ1 understates absolute adoption and RQ2 understates the
AI-vs-control gap (or moves it in an unknown direction).

### 1.6 "Rejected" is observable; the *reason* for rejection is not

§6.3 reports OR=6.7214 for agentic-PR rejection
(95 % CI [4.59, 9.84], p=1.22e-22). The dataset cannot distinguish
"rejected for security reasons" from "rejected because exploratory,"
"rejected for style/scope," or "closed by the author." The §6
[HUMAN REVIEW] block says so explicitly:

> *agentic PRs are rejected at a much higher rate*, not as
> *agentic PRs are rejected because of security*.

Readers should treat the OR=6.7 figure as a finding about
**maintainer disposition toward agentic PRs**, not about security.

## 2. Internal validity

Is the AI-vs-control comparison causal?

### 2.1 Match conditions on observables only

Phase B (`analysis/scripts/phase_b_match.py`) exact-matches on
language × stars-bin × created-year × owner-type and calipers on
z-scored `(log_stars, n_in_window_prs)` with a 0.25-σ caliper and
`replacement=False`. Unobservables — maintainer security-mindedness,
organisational policy, contributor base, funding, regulatory
exposure — are exactly the variables that drive both AI adoption and
security-tool configuration.

The §5.5 main table shows the unadjusted Fisher OR collapses to the
adjusted GLM OR for every BH-significant row:

| level | OR (Fisher) | adj_OR (GLM) |
| :-- | --: | --: |
| sast | 3.1166 | 0.4579 |
| sca  | 3.364  | 0.4293 |
| ci_hardening | 2.8658 | 0.4988 |
| codeql       | 3.1286 | 0.4562 |
| dependabot   | 3.1225 | 0.4635 |
| renovate     | 3.8603 | 0.3751 |

The GLM controls for `log_stars`, `language`, `repo_age`, `activity`,
`owner_type` and **reverses direction** on every row. The abstract
quotes the unadjusted OR; both numbers sit in the same table without
the report explicitly resolving which one to believe. A reader
should not interpret §5 as evidence that AI-coding *causes* higher
security-tool adoption — the observable-confounder shrinkage alone
explains the apparent effect.

### 2.2 Phase B was resumed mid-run

§3 footnote: a GitHub rate-limit hit at ~1000 candidates screened
forced a resume. The resume re-ran `--step screen` (1444 cache hits +
2647 live calls) and `--step match`, growing the matched-pair count
693 → 1744. NN matching with `replacement=False` is order-dependent
on candidate iteration; a resume changes that order. The seed
(`RANDOM_SEED=20260101`) is fixed, but byte-identical re-execution
requires recreating the rate-limit timing, which is not reproducible
from the artefacts.

### 2.3 Singleton-repo drop discards 79 % of RQ3 repos

§6.1: 2803 repos → 588 repos; 37,670 PR-rows → 13,249. The FE
estimator is identified only on repos with both PR types in window,
so the canonical RQ3 cohort is a non-random subset of the AI
cohort — likely the larger / more active / more bot-friendly tail.

The `any_security_intervention` headline (OR=0.5426) is fitted on
**6,212 obs across 100 repos** (§6.3), an even smaller subset.
Generalising any RQ3 OR to "AI-coded repos" is unsupported; the
estimand is "within-repo agentic-vs-human, in the subpopulation that
produces both PR types in a 7-month window."

### 2.4 `task_type` is forced off the RHS

§6.2: AIDev does not label `pr_task_type` on human PRs, so it is
perfectly collinear with the `agentic` indicator inside the FE
design. The analyst dropped it. The canonical RQ3 OR therefore
confounds "agentic" with "the work-type mix that agents are sent to
do" (likely heavier on bugfix and dep-update than human PRs). This
is documented in REPORT.md as "a design forced by the dataset," not
a finding — but the implication is that the residual RQ3 effect
cannot be attributed to PR authorship alone.

## 3. External validity

Where do the findings generalise?

### 3.1 Single window, single dataset, single platform

- 7 months: 2025-01-01 → 2025-07-31.
- Single corpus: AIDev v3 curated subset (33,596 agentic PRs across
  2,807 repos).
- Single platform: GitHub.
- Single popularity floor: ≥100 stars.

Pre-2025 patterns of AI-tooling and security adoption may differ;
<100-star repos and private/enterprise repos are absent; CI run on
GitLab, CircleCI, Buildkite, or self-hosted Jenkins is invisible to
Phase C.

### 3.2 Curation selects on visible self-attribution

AIDev's own classifier and the study's
`configs/agent_fingerprints.yaml` both reward agents that announce
themselves in PR bodies and commit trailers. "Agentic" therefore
skews toward verbose-attribution agents (Devin, Codex, Cursor and
similar) over silent ones, which in turn affects both arms of every
RQ3 within-repo comparison.

## 4. Statistical-conclusion validity

### 4.1 Realised power < pre-flight power on the headline outcomes

§7.2: pre-flight predicted achieved-power 0.8149 / 0.9996 on
`any_security_intervention` / `rejected`; the post-hoc table gives
0.5732 / 0.6757. Nine RQ3 rows have realised FE SE exceeding the
Kish-DEFF closed-form; they are flagged in
`analysis/tables/power_analysis.csv` via the gap between
`achieved_power_pre` and `achieved_power_post`. Headlines survive,
but the registered margin was overstated.

### 4.2 The sparse-band threshold is a researcher degree of freedom

§5.2 excludes 15 of 19 tools (control rate < 1 %) from the BH
family, leaving m=4. Moving the threshold to 0.5 % or 2 % would
change the BH family and the `p_adj` values for the four retained
tools. The rule is principled (informed by `rq2_per_tool` MDE
pre-flight) but is not itself preregistered with a sensitivity
check.

### 4.3 Mixed estimators across the §6.3 row block

The three "primary outcomes" mix three estimators:

| outcome | model |
| :-- | :-- |
| `any_security_intervention`   | logit_fe |
| `security_intervention_count` | poisson_quasi (NB-regularised fallback per `rq3_compute.py:fit_count_fe`) |
| `rejected`                    | logit_fe |

The cluster-robust sandwich is rank-deficient on some rows (~600 FE
columns vs 588 clusters); the code falls back to HC1 silently in
those cases. Comparing CI widths across the three rows compares
different estimators on different fallback paths.

### 4.4 Two pre-declared underpowered families

`rq2_secrets` and `rq2_fuzzing` have achieved power 0.36 / 0.20
(§7.3) and are correctly labelled "not informative." The §4.1
descriptive headlines still surface their adoption rates
(`secrets` 0.963 %, `fuzzing` 0.392 %) alongside the well-powered
RQ1 numbers; a casual reader will read the wide RQ2 CIs spanning 1
as null findings.

### 4.5 No cross-family FDR control

BH is applied within explicit families (m=5 categories, m=4 retained
tools, three RQ3 outcomes). Across the report's ~30 declared
hypothesis tests (RQ2 categories + tools + RQ3 three primary +
robustness × 4 variants × 3 outcomes + secondary nonparametric),
there is no global correction. The headline rejections (sast OR=3.12
p_adj=6.92e-29; rejected OR=6.72 p=1.22e-22) survive any reasonable
global procedure; borderline rejections — e.g. `security_intervention_count`
p_raw=0.0309 — would not.

## 5. Other threats worth flagging

### 5.1 Configs revision happened after a first run

§9: the post-clean configs were chosen *with knowledge* of the
pre-clean direction on RQ3. The audit-then-revise-then-rerun
sequence is documented honestly, but the choice of which patterns
to drop and which to add is endogenous to having seen the pre-clean
results. Robustness variant `v5_bot_identity_only` partially
defends against this: it strips the keyword detector entirely and
confirms `rejected` survives (OR=6.7132 vs 6.7214) — but
`any_security_intervention` does *not* survive v5, so the canonical
headline on that outcome is partly methodology-locked-in.

### 5.2 Dataset-version pin is by string, not by hash

§10 lists the AIDev DOI `10.5281/zenodo.16919272`, version `v3`, and
the uv lockfile sha256, but no content-hash of the AIDev tables
themselves is republished in REPORT.md. If Zenodo silently updates a
record in place (rare but possible), reruns will diverge. The
`run_manifest.json` carries an `aidev_dataset_sha` field for this
reason; it should be cited in any pre-publication audit.

### 5.3 Notebook outputs are regenerated, not pinned

The four tutorial notebooks under `analysis/notebooks/` are paired
via Jupytext and re-executed by `analysis/scripts/render_notebooks.sh`
on every build. Cell outputs in the committed `.ipynb` therefore
reflect *the most recent local rebuild*, not a pinned snapshot. A
reader who re-renders against a different `data_derived/<date>/`
will see different inline values from those a downstream commenter
might quote.
